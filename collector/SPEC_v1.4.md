**版本**：v1.4（论文实战精简执行版 · 基准日 2026-11-20）

## 三、 轻量化单进程双活采集器与数据落盘契约

### 3.1 架构收口原则（去重型平台化）
* **单 Rust 二进制进程**：可参考 `nkaz001/hftbacktest` 官方 Rust `collector`（锁定具体参考 commit）的 `tokio` 异步结构，但须替换为本方案的有界队列（`mpsc::channel` 固定容量）、双活状态机与统一落盘格式。**不拆外部独立发布进程，不建多套冗余索引表**。
* **热路径铁律**：接收线程拿到完整 WS 应用消息后，在 JSON 解析前立刻打下 **`recv_wall_ns`**（UTC 墙钟）与 **`recv_mono_ns`**（本机单调递增钟），仅做轻量状态校验与主备选择，绝不在热路径做复杂盘口重建或二次 JSON 序列化。

### 3.2 A/B 双活因果热备与“单份主线落盘”机制

```text
                +----------------------------------------+
                |   Exchange WS Endpoint (e.g. Gate)     |
                +-------------------+--------------------+
                                    |
            +-----------------------+-----------------------+
            | (00:00 UTC 平滑轮换)                            | (12:00 UTC 平滑轮换)
            v                                               v
   +------------------+                            +------------------+
   |   WS Conn A      | (独立状态机: WAIT_ANCHOR    |   WS Conn B      |
   |  (主线 Primary)   |  -> LIVE -> INVALID)      | (热备 Standby)    |
   +--------+---------+                            +--------+---------+
            |                                               |
            +-----------------------+-----------------------+
                                    v
             +---------------------------------------------+
             |  单进程内因果切换器 (Causal Selector)         |
             |  • 默认只放行当前主线 (A)；严禁跨线拼接增量    |
             |  • 主线失效或计划轮换时，仅当备线已 LIVE 切换  |
             |  • 每次切换/缺口写结构化 _meta 记录           |
             +----------------------+----------------------+
                                    v
             +---------------------------------------------+
             |  单份规范原始流 (按小时切分 Zstd-3 + SHA-256) |
             |  仅存原样 UTF-8 字节 (严禁 payload_b64)       |
             +---------------------------------------------+
```

1. **A/B 独立建簿状态机（绝不跨线拼序列）**：
   * 每个交易所/端点维护 **Conn A**（主线）与 **Conn B**（热备）两条独立 TCP/WS 连接（Binance 的 `/public` 与 `/market` 各自维护 A/B 对）。
   * 两条连接在内存中各自独立维护协议状态（`WAIT_ANCHOR` $\to$ `LIVE` $\to$ `INVALID` $\to$ `RESYNC`），**严禁将 A 的增量和 B 的增量交替拼接去修补跳号**。
2. **严格因果切换 + 仅落盘单份流（省一半磁盘与 AWS 出站流量）**：
   * 正常状态下只将当前主线（如 A）的原始帧写入磁盘，备线（B）在内存中实时保持同步和校验但不重复落盘。
   * **计划内错峰轮换**：在交易所 24h 强踢前，每日 `00:00:00 UTC` 轮换 A（先切主线到已 `LIVE` 的 B 并写入 `SWITCH` 元记录，再安全关闭并重启 A 直至 A 重新 `LIVE`）；每日 `12:00:00 UTC` 同理轮换 B。计划内轮换断层严格为 **`0 ms`**。
   * **异常故障切换**：主线发生断连、心跳超时或序列破坏时，若备线当前处于 `LIVE` 状态，立即在当前真实时刻切换主线至备线并写入 `SWITCH` 记录（同时触发一次新基准快照确保离线重建无缝，不倒写过去时间戳）；若备线也未就绪，则写入 `GAP_START` 直到任一线重新 `LIVE` 写入 `GAP_END`。
3. **智能静音看门狗（防清淡币种误判重连）**：
   * 某条流连续 `3 秒` 无新行情时，**不直接强踢连接**，而是触发活性诊断：核查连接级 `ping/pong`、该频道静默语义、同连接其他币种（如 BTC）是否仍在推帧以及备线状态。仅当协议心跳超时、读错误或确认该连接整体僵死时才重连（带抖动退避），且绝不同时重启健康的备线。
   * 有界队列满或写盘阻塞时，绝不静默丢包，必须写 `LOCAL_LOSS` 元记录并触发告警。

### 3.3 原始落盘格式（字节级无损 + 高压缩比，禁用 `payload_b64`）
采用**制表符分隔的原始 UTF-8 文本行**（TSV-Raw，若原始字节偶含 `\n`/`\r` 则拒绝混入并单独转义记录，保证字节往返测试 100% 一致），彻底避免 Base64 造成的 33% 体积膨胀与 `zstd` 压缩率劣化：

```text
# 格式：recv_wall_ns \t recv_mono_ns \t conn_id \t epoch \t rx_seq \t kind \t raw_utf8_json_payload \n
1795478400123456789	98412000123	A	1	409812	DATA	{"channel":"futures.obu","event":"update",...}
1795478400124100222	98412643556	B	1	409813	META	{"event":"SWITCH","from":"A","to":"B","reason":"planned_rotation","symbol":"ALL"}
```

* 每条记录保留 `boot_id`（写在小时文件头或独立 `manifest` 中）、`conn_id`、`epoch`（每次重连递增）、`rx_seq`（本机单调帧序号），以及未经二次序列化的交易所原始 UTF-8 载荷。
* **跨 UTC 小时无缝切分**：每逢整点无缝切换新文件，不断开 WS 连接、不重置内存盘口状态；每所每小时为 1 个逻辑分区（4 所每天共 96 个小时分区，按清单管理，不硬写死文件总数）。

### 3.4 轻量元数据与监控守护脚本（`meta_daemon.py`）
独立于 Rust 采集进程，避免干扰主线程：
* **合约规格采集**：在**程序启动时 + 每日 `00:00:00 UTC` + 任一交易所发生重连后**拉取表 2 所列 4 所完整 REST 合约规格，原样保存 JSON（含查询/回复时间戳、内容指纹、tick/lot/乘数/费率说明），存入 `meta/specs/`（无需盘中每 5 分钟高频轮询）。若前后两次观察规格变动但生效时刻不明，离线质检将该区间标为隔离，绝不倒推。
* **网络 RTT 与系统时钟记录**：每 `5 分钟` 测一次到 4 所公开网关的 RTT 存入 `meta/rtt/rtt_YYYYMMDD.csv`（288 槽/天）；每 `1 分钟` 记录一次 `chronyc tracking` 的源、offset、root delay 与 root dispersion 存入 `meta/chrony/chrony_YYYYMMDD.csv`（1,440 槽/天）。
* **即时告警**：A/B 双线同时断开超 `5 秒`、`LOCAL_LOSS` 触发、或本地磁盘占用超 `70%` 时，通过 Webhook / Telegram 告警。

## 四、 AWS 东京基础设施、单 Google Drive 原子归档与预算

### 4.1 AWS 东京主机与时钟规范
* **物理可用区**：通过 `aws ec2 describe-availability-zones --region ap-northeast-1` 查实物理 ID 并锁定 **`apne1-az4`**（与 Binance `fstream` 及 Bybit 2026-11-12 迁东京后的核心交易服务同可用区）。不为了挑某个币的微秒表现而“抽卡”换机器；开机跑 10 分钟四所 RTT 预检，确认中位数在同城 `0.5–5.0 ms` 且无抖动即固定。
* **实例与存储**：候选 **`c7i.large`** 或 **`c6i.large`**（2 vCPU / 4 GB RAM，非积分型固定计算实例，注：不宣称为物理核独占）+ **100 GB EBS `gp3`** + **Public Subnet 直接分配公网 IPv4**（开启 ENA，**严禁走 NAT Gateway**，禁用公开 SSH 弱口令，凭据仅存本机受限权限文件）。
* **对时配置**：`/etc/chrony/chrony.conf` 首行指向 AWS 本地 NTP 服务 `169.254.169.123`（`prefer iburst minpoll 4 maxpoll 4`，不虚称为直接硬件 PHC）。离线质检对 `chrony` 估计误差超过 `1 ms` 或失步的区间标记为时序不可认证。

### 4.2 单 Google Drive Pro（5 TB）原子直传归档
首版**仅采用 EC2 直传单个已授权 Google Drive Pro 账户（`gdrive_main:`，5 TB）**，不引入 CloudFront 与 Colab，使用自建 Google Cloud OAuth Client ID 配合 `rclone` 防止公共配额限流。

目录规范：
```text
gdrive_main:tokyo_l2_data/
├── raw/{binance_futures,bybit_linear,bitget_v3,gate_futures}/YYYY-MM-DD/
│   ├── {exchange}_YYYYMMDD_HH.tsv.zst
│   └── {exchange}_YYYYMMDD_HH.manifest.json   # 含 boot_id、sha256、字节数、起止时刻与计数
├── meta/{specs,rtt,chrony}/...
└── qa_reports/YYYY-MM-DD/...
```

**每小时原子封口与归档流程（每小时第 05 分触发）**：
1. 封口上一小时文件：`.partial` $\to$ `flush/fsync` $\to$ `zstd -t` 完整性解压检验 $\to$ 计算 `SHA-256` 与字节数 $\to$ 原子改名并写出对应 `.manifest.json`。
2. `rclone copy` 幂等上传不可变对象至 `gdrive_main:`；若远端已存在同名但哈希不同的对象，立刻告警隔离，禁止覆盖。
3. **远端真实验证**：通过 Drive API / `rclone` 核对远端文件 ID、字节数与远端内容哈希（Google Drive API 原生返回文件 MD5/SHA-256 校验字段；若不可用则执行抽样/回读校验），核对通过后写入本地已验账本。
4. **本地滚动缓冲清理**：仅清理“远端已验真”且超过本地安全滚动缓冲期（如 24 小时）的旧文件；远端失败或磁盘未达阈值前绝不删源。

### 4.3 磁盘冗余与预算口径（以 P2 24h 试采实测为准）
* **磁盘防爆盘公式**：设留足系统与运行余量后的可用空间为 $B_{\text{free}}$，P2 试采最忙小时全四所合计压缩字节为 $R_{\text{peak}}$，验收要求满足至少抗住 48 小时上传中断且保留 20% 冗余：
  $$0.8 B_{\text{free}} \ge 48 R_{\text{peak}}$$
* **粗估参考（非保证值，P2 后用实测替换）**：采用单份规范流 + 无 Base64 的 `zstd -3` 压缩，预计日压缩体积约 **`12 – 18 GB / 天`**（30 天约 `360 – 540 GB`，仅占单 5 TB 盘约 10%）。AWS 东京每月首 `100 GB` 出站免费，超出按 `$0.114 / GB` 计；21–30 天完整周期（含 `c7i.large` `$0.1123/hr`、100 GB `gp3`、IPv4 与出站费）预估约 **`$80 – $140`**。若 24h 试采发现单日体积显著高于预期，P2 结束时再决定是否按月启用 S3 + CloudFront 1 TB 免费中转。

## 五、 离线质检门禁与 `hftbacktest` 回放契约

1. **独立通道严格分离（防混合伪造）**：
   * `research_bindings.json` 明确绑定：Binance `@bookTicker` 作为跨所信号源；各跟随所的独立一档流（`book_ticker` / `orderbook.1` / `books1`）与 50 档 L2 流分别保留，**严禁把一档流强行覆盖进 50 档撮合簿或重复推送市场成交**。
   * HBT `.npz` 转换时，用交易所原始事件时间驱动模拟撮合，用规范视图实际到达/发布的本地时间驱动策略决策；同一 WS 消息内的多档更新必须保持原子边界（全部处理完再唤醒策略），严禁靠人为加固定延迟掩盖帧边界问题。主回测是否叠加额外 `2.5 ms` 跨所延迟须在 `freeze.json` 显式声明，避免重复计入已实测的本地网络传输时间。
2. **50 档深度覆盖率实测与 `QUEUE_UNKNOWN` 红线**：
   * P2 试采期用冻结策略统计**拟报价格、在场活单价格、模拟成交价格**落在各侧第 50 个非空价位边界内的比例（按时间、订单与成交加权）。
   * 凡超出可见 50 档边界的挂单，一律标记 **`QUEUE_UNKNOWN`**，**严禁当作空队列（`queue = 0`）排在队首成交，也严禁只删亏损的超界成交**。若试采发现某币种超界比例显著偏高，必须在正式盲采前于 `freeze.json` 中预先决定处理规则（如开启可见深度截断对照或单列该对边界限制）。
3. **缺口处理铁律（不掩盖队列污染）**：
   * 任何未被健康备线覆盖、影响撮合连续性的 `GAP` 或 `LOCAL_LOSS` 窗口，不能只靠事后剔除缺口前后 $\pm 5\text{s}$ 成交假装整日队列无损。
   * **默认日级主表规则**：当日某资产对若出现未覆盖的撮合缺口，该资产日标记为 **`execution_unverified`**（在最终日历资格表中保留席位并注明原因，不静默删除、不补日凑数）；如需分析有效片段，须在附表独立初始化并经过完整 `600 秒` 预热。所有 Markout 标签严禁跨越任何所需流的无效区间。
4. **评价指标与主口径统一**：
   * 完全沿用主研究仓库 R1/R2 冻结后的统一口径：主指标为**单位成交额毛收益（`gross_bps`）**、**成交价基准 `Total Markout`（`100ms` / `500ms` / `1000ms`，显式汇报两端报价年龄与同报价复用率，并附独立 BBO vs L2 顶档同成交交集敏感性）**、**有效交易段标准化库存风险（`pos_std` 与 `pos_std / order_qty`）**，以及 Net USDT 严格三项拆解（`fee_saved + vol_shrink_gross + quality_gross`）与 `0 / -0.5 / +2 bps` 多费率映射。
